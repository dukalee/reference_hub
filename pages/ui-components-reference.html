§

사용 빈도 랭킹 Top 20

특정 라이브러리에 묶이지 않는, 어떤 화면에서든 마주치는 기본 UI 구성요소 20가지입니다. 프레임워크가 바뀌어도 이 요소들이 하는 "역할"은 그대로입니다.

§

먼저 알아야 할 4가지

개별 컴포넌트를 외우기 전에 이 네 가지를 이해하면, 어떤 프레임워크·디자인 시스템을 쓰든 UI를 읽고 만드는 방식이 크게 달라지지 않습니다.

① 상태(State) — 요소는 항상 여러 얼굴을 가진다

버튼이든 입력창이든, 완성된 컴포넌트는 최소 5가지 상태를 갖습니다: 기본(default), hover(마우스 올림), focus(키보드로 선택됨), active(누르는 중), disabled(비활성). 디자인 목업엔 기본 상태만 그려져 있는 경우가 많아, 나머지 상태를 직접 챙기는 것이 UI 구현의 8할입니다.

실습 예시

마우스를 올려보고(hover), 클릭한 채로 눌러보고(active), Tab 키로 포커스를 옮겨보세요(focus). 특히 focus 상태를 마우스 클릭만으로는 확인할 수 없습니다 — 키보드 사용자를 위해 outline을 절대 display:none으로 지우지 마세요.

② label과 접근성 — 눈에 안 보여도 연결은 되어 있어야 한다

모든 입력 요소는 <label>과 짝을 이뤄야 합니다. for·id를 연결하면 라벨 텍스트를 클릭했을 때도 입력에 포커스가 가고, 스크린 리더가 "무엇을 입력하는 칸인지" 읽어줄 수 있습니다. placeholder는 라벨의 대체재가 아닙니다 — 값을 입력하는 순간 사라지기 때문입니다.

실습 예시

위 "이메일" 글자를 클릭해보세요 — label[for]이 연결돼 있으면 라벨을 눌러도 옆 입력창에 포커스가 잡힙니다.

③ 네이티브 요소 vs 커스텀 위젯

브라우저 기본 <select>, <input type="checkbox"> 같은 요소는 키보드 내비게이션·스크린리더 지원·모바일 네이티브 UI가 공짜로 따라옵니다. 디자인 통일성을 위해 커스텀 위젯을 만들 땐, 이 페이지의 체크박스·라디오·토글·별점처럼 실제 <input>은 숨기고 그 위에 스타일만 새로 그리는 방식을 권장합니다 — 시각적으로는 완전히 바뀌어도 접근성·폼 제출 동작은 그대로 유지됩니다.

실습 예시

④ 터치 타겟과 상대 단위

모바일에서 손가락으로 정확히 누를 수 있는 최소 크기는 대략 44×44px입니다(iOS HIG 권장 기준). 아이콘 버튼을 24px 아이콘 그대로 클릭 영역으로 두지 말고 여백(padding)으로 타겟을 키우세요. 크기 단위는 브라우저 글자 크기 설정을 존중하도록 px 대신 rem/em을 우선 고려합니다.

실습 예시

왼쪽(24px)과 오른쪽(38px, 위 .ui-icon-btn 기본값)을 비교해보세요. 시각적 아이콘 크기는 비슷해 보여도 실제로 누를 수 있는 영역 차이가 모바일에서는 오클릭률을 좌우합니다.
A

텍스트 입력

5 components

사용자가 자유 형식의 값을 타이핑하는 요소들입니다. type 속성만 바꿔도 모바일 키보드 배열과 브라우저 검증 규칙이 달라집니다.

#02

Text Field (한 줄 입력)

가장 기본적인 자유 입력란입니다. 이름, 검색어, 짧은 값 등 한 줄로 끝나는 모든 입력의 기본형이며, 다른 대부분의 입력 요소(숫자, 이메일, 비밀번호)는 이 요소의 변형입니다.

실습 예시

placeholder는 값이 아니라 힌트입니다. 폼 제출 시 placeholder 텍스트는 절대 전송되지 않으므로, 기본값이 필요하면 value 속성을 쓰세요.
#—

Textarea (여러 줄 입력)

후기, 설명, 코멘트처럼 여러 줄에 걸친 텍스트를 받을 때 씁니다. 기본적으로 사용자가 크기를 드래그로 조절할 수 있어(리사이즈 핸들), 레이아웃이 깨지지 않는 선에서 허용해주는 것이 사용성에 좋습니다.

실습 예시

오른쪽 아래 모서리를 드래그해 크기를 조절해보세요. resize:none으로 막을 수도 있지만, 긴 글을 쓰는 사용자에겐 불편할 수 있으니 신중히 사용하세요.

Search (검색창)

type="search"은 겉보기엔 텍스트 필드와 같지만, 데스크톱 브라우저에서 값을 입력하면 자동으로 지우기(×) 버튼이 나타나고, 모바일 키보드의 Enter 키가 "검색"으로 바뀝니다.

실습 예시

Number (숫자 입력)

type="number"은 값 증감 화살표(스피너)가 함께 제공되고, 모바일에서는 숫자 키패드가 뜹니다. min/max/step으로 허용 범위를 제한할 수 있습니다.

실습 예시

숫자만 저장하고 싶다고 해서 전화번호·우편번호에 type="number"를 쓰지 마세요. 앞자리 0이 사라지고, 스피너 화살표가 의미 없이 붙습니다. 이런 값은 type="text" + inputmode="numeric"이 정답입니다.

그 밖의 입력 타입 (email · password · date · color · file …)

<input>은 type 하나만 바꿔도 완전히 다른 네이티브 UI와 검증 규칙을 제공합니다. 직접 만들지 말고 우선 이 표에서 맞는 타입을 찾아보세요.

type제공되는 UI용도
email@ 포함 여부 자동 검증, 모바일 @ 키 노출이메일 주소
password입력값 마스킹(●●●)비밀번호
date네이티브 달력 피커생년월일, 예약일
color네이티브 색상 선택기테마 색상 지정
file파일 탐색기(찾아보기 버튼)업로드
tel모바일 전화 키패드전화번호(형식 검증은 별도 필요)
urlURL 형식 자동 검증웹사이트 주소

실습 예시

B

선택 입력

4 components

정해진 값 중에서 고르는 요소들입니다. 자유 입력보다 오타·형식 오류가 없어 데이터 품질이 좋아집니다.

#03

Checkbox (체크박스)

하나의 값을 켜고 끄거나(약관 동의), 여러 항목을 동시에 선택할 때 씁니다. 라디오와 헷갈리기 쉬운데 기준은 간단합니다 — 여러 개를 동시에 선택 가능하면 체크박스, 하나만 고를 수 있으면 라디오입니다.

실습 예시

실제 <input type="checkbox">는 화면에서 투명 처리하고 그 위에 <span class="box">로 체크 모양을 그린 구조입니다 — 클릭·키보드·폼 제출 동작은 네이티브 체크박스 그대로 유지됩니다.
#04

Radio Button (라디오 버튼)

같은 name을 공유하는 라디오 버튼 그룹 중에서 정확히 하나만 선택됩니다. 옵션이 2~5개 정도로 적고 항상 화면에 다 보여줘도 괜찮을 때 <select>보다 라디오가 낫습니다 — 비교가 쉽기 때문입니다.

실습 예시

세그먼트형 변형

같은 "하나만 선택" 로직을 칩(chip) 형태로 그리면 세그먼트 컨트롤이 됩니다. 필터·정렬 기준처럼 짧은 옵션을 나란히 보여줄 때 자주 쓰입니다.

#09

Toggle Switch (토글 스위치)

내부적으로는 체크박스와 똑같이 on/off 두 상태지만, "즉시 적용되는 설정"이라는 의미를 시각적으로 강조합니다. 다크 모드, 알림 켜기/끄기처럼 저장 버튼 없이 바로 반영되는 설정에 씁니다 — 폼 제출이 필요한 동의 항목엔 체크박스를 쓰세요.

실습 예시

#05

Select (드롭다운 선택)

옵션이 많거나(6개 이상) 화면 공간이 좁을 때, 네이티브 <select>는 평소엔 한 줄만 차지하다가 클릭하면 전체 목록을 펼쳐줍니다. 모바일에서는 OS의 네이티브 휠/시트 UI로 자동 전환됩니다.

실습 예시

타이핑으로 자동완성이 필요하면 <input list="id"> + <datalist id="id"> 조합(콤보박스)을 검토하세요 — 자유 입력과 추천 목록을 동시에 지원합니다.
C

범위·평가·진행

3 components

정확한 숫자보다 "대략적인 위치·양·정도"를 다루는 요소들입니다.

#17

Range Slider (슬라이더)

최소~최대 사이의 값을 드래그로 고릅니다. 숫자 입력보다 직관적이지만 정확한 값을 타이핑할 수 없다는 단점이 있어, 정밀한 값이 중요하면 숫자 입력을 함께 보여주는 것이 좋습니다.

실습 예시

Rating (별점)

만족도·품질처럼 정성적인 값을 5단계 내외로 빠르게 입력받을 때 씁니다. 내부는 라디오 버튼 그룹이며, 별 아이콘은 CSS로 그려진 라벨일 뿐입니다.

실습 예시

별 5개를 HTML에서 역순(5→1)으로 배치하고 flex-direction:row-reverse로 화면에서만 다시 뒤집는 것이 핵심 트릭입니다. 그래야 "hover한 별부터 그 왼쪽까지 전부 채우기"를 ~(형제) 선택자만으로 구현할 수 있습니다.
#14

Progress Bar (진행률 표시줄)

업로드·설치처럼 끝이 예측 가능한 작업의 진행 정도를 보여줍니다. 끝을 알 수 없는 대기 상태(서버 응답 기다림 등)에는 진행률 바 대신 스피너를 쓰는 것이 맞습니다.

실습 예시

첫 번째 줄은 네이티브 <progress> 요소(브라우저 기본 스타일), 두 번째 줄은 div 두 개로 직접 그린 커스텀 버전입니다. 디자인 자유도가 필요하면 커스텀 쪽을, 접근성을 최소 노력으로 챙기려면 네이티브 쪽을 선택하세요.
D

버튼과 액션

3 components

사용자의 의도적인 클릭으로 어떤 동작을 실행시키는 요소들입니다.

#01

Button (버튼 변형)

한 화면에 버튼이 여러 개 있을 때 시각적 위계가 필요합니다. Primary는 화면당 보통 하나(가장 원하는 행동), Secondary는 대안 행동, Ghost는 부가 행동, Danger는 삭제처럼 되돌리기 어려운 행동에 씁니다.

실습 예시

한 화면에 primary 버튼을 여러 개 두면 사용자가 뭘 눌러야 할지 판단하는 데 시간이 걸립니다. "가장 하이라이트된 행동"은 화면(혹은 카드) 하나당 원칙적으로 하나만 두세요.

Icon Button (아이콘 버튼)

텍스트 없이 아이콘만으로 동작을 표시합니다. 공간을 아낄 수 있지만 의미가 명확한 아이콘(닫기 ✕, 검색 🔍)에만 써야 하며, 스크린 리더를 위해 반드시 aria-label로 텍스트 설명을 붙여야 합니다.

실습 예시

Link 버튼 (텍스트 링크)

버튼처럼 스타일링된 <a>와, 밑줄만 있는 순수 텍스트 링크는 다릅니다. 페이지 이동이면 <a href>, 같은 페이지에서 상태만 바뀌는 동작이면 <button>을 쓰는 것이 시맨틱상 올바릅니다 — 겉모습이 같아 보여도 내부 태그는 역할에 맞춰야 합니다.

실습 예시

버튼처럼 보이는 링크 밑줄 텍스트 링크
E

네비게이션

4 components

"지금 어디에 있고, 어디로 갈 수 있는지"를 알려주는 요소들입니다.

#08

Tabs (탭)

같은 층위의 콘텐츠를 여러 개 두고, 한 번에 하나씩만 보여줄 때 씁니다. 페이지 이동 없이 전환된다는 점에서 링크 내비게이션과 다릅니다. 탭이 7개를 넘어가면 스크롤이 생기거나 드롭다운으로 접는 것을 고려하세요.

실습 예시

제품 개요 내용이 여기 표시됩니다.
상세 사양 표가 여기 표시됩니다.
사용자 리뷰 목록이 여기 표시됩니다.
JavaScript 없이 숨은 라디오 버튼 + :checked ~ 형제 선택자만으로 동작합니다. 실무에서는 접근성(role="tablist", 화살표 키 이동)까지 챙기려면 JS 기반 구현이 더 안전합니다.

Breadcrumb (경로 표시)

깊은 계층 구조 안에서 현재 위치와 상위 경로를 보여줍니다. 사용자가 중간 단계로 한 번에 돌아갈 수 있게 해, "뒤로가기"를 여러 번 누르지 않아도 됩니다.

실습 예시

홈/ 라이브러리/ Gradio

Pagination (페이지네이션)

긴 목록을 여러 페이지로 나눠 번호로 이동합니다. 무한 스크롤과 달리 특정 위치로 다시 돌아오기 쉽다는 장점이 있어, 검색 결과·게시판처럼 "몇 번째"가 중요한 목록에 적합합니다.

실습 예시

Dropdown Menu (네비게이션 메뉴)

버튼이나 아바타를 클릭하면 관련 행동 목록이 펼쳐지는 메뉴입니다. Select와 다른 점은, 메뉴 항목이 "값 선택"이 아니라 "각각 다른 동작 실행"이라는 것입니다.

실습 예시

내 계정
프로필 보기 설정 로그아웃
네이티브 <details>/<summary>로 만들면 클릭·Enter·Space 토글이 브라우저에서 공짜로 제공됩니다.
F

오버레이·컨테이너

4 components

콘텐츠를 접었다 펼치거나, 화면 위에 떠 있는 레이어로 보여주는 요소들입니다.

#13

Accordion (아코디언)

제목만 보여주다가 클릭하면 내용이 펼쳐지는 목록입니다. FAQ처럼 한 번에 하나씩만 훑어봐도 되는 긴 콘텐츠를 처음부터 다 펼쳐두지 않아 화면을 짧게 유지해줍니다.

실습 예시

배송은 얼마나 걸리나요?
평균 2~3영업일 내 도착합니다. 도서산간 지역은 1~2일 추가될 수 있습니다.
환불은 어떻게 하나요?
수령 후 7일 이내, 마이페이지에서 신청할 수 있습니다.
네이티브 <details>는 그 자체로 완전히 동작하는 아코디언입니다 — 위 CSS는 화살표 아이콘과 테두리만 입힌 것으로, 토글 로직에는 전혀 관여하지 않습니다.
#06

Modal (모달 다이얼로그)

현재 화면 위에 떠서 다른 조작을 막고(모달), 확인이 꼭 필요한 정보나 짧은 폼을 받을 때 씁니다. 뒤 배경을 어둡게(오버레이) 처리해 "지금은 이것부터 처리해야 한다"는 것을 알려줍니다.

실습 예시

삭제 확인 모달 열기
정말 삭제하시겠어요?

이 작업은 되돌릴 수 없습니다.

삭제 취소
JavaScript 없이 href="#id" 링크와 CSS :target 가상 클래스만으로 열고 닫습니다. 실무에서는 <dialog> 요소나 포커스 트랩(모달 밖으로 Tab이 빠져나가지 않게)까지 챙기는 라이브러리 사용을 권장합니다.
#10

Tooltip (툴팁)

아이콘이나 축약된 텍스트에 마우스를 올리면(또는 포커스하면) 잠깐 나타나는 보조 설명입니다. 클릭해야만 알 수 있는 중요한 정보를 숨기는 용도로 쓰면 안 됩니다 — 어디까지나 "있으면 좋은" 부가 설명용입니다.

실습 예시

QPS ⓘ
위 글자에 마우스를 올리거나 Tab으로 포커스를 옮겨보세요. :hover뿐 아니라 :focus도 함께 처리해야 키보드·터치 사용자도 툴팁을 볼 수 있습니다.

Card (카드)

이미지·제목·설명·행동 버튼처럼 서로 관련된 정보 묶음을 하나의 시각적 단위로 묶습니다. 목록·그리드 형태로 반복 배치되는 경우가 많아, 이 사이트의 라이브러리 카드도 같은 패턴입니다.

실습 예시

카드 제목

카드 안에는 이미지·제목·설명·행동이 한 묶음으로 들어갑니다.

마우스를 카드 위에 올려보세요 — 살짝 떠오르는(elevate) hover 효과는 "이 영역 전체가 클릭 가능하다"는 신호를 줍니다.

#11

Alert / Banner (알림 배너)

화면 흐름 안에 고정되어 표시되는 상태 메시지입니다. 몇 초 뒤 사라지는 토스트와 달리, 사용자가 직접 닫기 전까지(또는 원인이 해결되기 전까지) 남아있는 경우가 많습니다.

실습 예시

일부 브라우저에서는 이 기능이 지원되지 않을 수 있습니다.
오른쪽 ✕를 눌러보세요. 숨겨진 체크박스가 "닫힘" 상태를 기억하고, :checked ~ .ui-alert{display:none} 형제 선택자로 알림을 감춥니다 — JS 없이 닫기 버튼을 구현하는 흔한 트릭입니다.
#12

Badge · Tag (뱃지 · 태그)

Badge는 상태·개수를 나타내는 작은 표식(알림 개수, "NEW"), Tag는 분류·키워드를 나타내며 종종 삭제 가능한 형태로 쓰입니다. 이 사이트의 .tag.new, .rank 배지도 같은 계열입니다.

실습 예시

사용자를 나타내는 원형 이미지 또는 이니셜입니다. 우측 하단에 작은 점(status dot)을 얹어 온라인/오프라인 같은 실시간 상태를 함께 표시하는 경우가 많습니다.

Spinner (로딩 스피너)

얼마나 걸릴지 예측할 수 없는 짧은 대기 상태(서버 응답 등)를 나타냅니다. 순수 CSS 애니메이션(@keyframes 회전)만으로 구현되며, 사용자에게 "멈춘 게 아니라 처리 중"이라는 확신을 줍니다.

실습 예시

3초 이상 걸리는 작업이면 스피너만으로는 불안감을 줄 수 있습니다 — 진행률을 알 수 있는 작업이라면 C. Progress Bar로 바꾸는 것을 검토하세요.

Skeleton (스켈레톤 로더)

실제 콘텐츠가 로드되기 전, 대략적인 레이아웃 모양(회색 블록)을 미리 보여줍니다. 빈 화면이나 스피너보다 체감 로딩 속도가 빠르게 느껴진다는 연구 결과 때문에 카드형 목록 로딩에 널리 쓰입니다.
